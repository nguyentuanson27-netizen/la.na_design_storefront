# Meta Ads audit — 2026-10-07

Base: `ffe0a596`, local branch `codex/meta-ads-audit`. Scope: direct browser Meta Pixel and direct Next.js/server CAPI. No GTM/sGTM migration, production deployment, external Meta events, or Business Manager settings changes.

## Catalog checkpoint

Meta Catalog is optional for the Pixel/CAPI tracking implemented here. Its absence does not block sending or validating the five website events. A Catalog and verified content mapping are needed when using catalog-based product ads; the checkpoint below applies before changing content ID semantics for that integration.

Owner confirmation: **Meta Catalog chưa kết nối**. There is no verified Catalog ID, connected Pixel ID, feed/export, or actual `id`/`retailer_id` sample. Consequently this change preserves the existing product-slug identity used by ViewContent/AddToCart. It does not choose a new SKU, product code, Pancake product/variation ID, or internal DB ID scheme.

The internal VariantMirror ID fallback in checkout is removed. An unresolved identity suppresses the Meta event, without rejecting commerce. New order lines freeze the committed source PDP slug. A single nullable `CartItem.sourceProductSlug` persists the full server PDP projection's proven selected option, so a component bought through a parent retains that parent even if the component owner is public. Cart quantity edits preserve it. Legacy private lines without provenance are not assigned a guessed parent. Historical order lines without that evidence are not backfilled from the mutable catalog. This establishes consistency inside the implementation; it does **not** establish a match with an actual Meta Catalog. Product versus variant identity and slug renames remain at this checkpoint.

Before a later mapping change: verify the intended Catalog ID and connected Pixel/dataset ID against a read-only feed/export and 2–3 actual product/variant `id` or `retailer_id` values with the corresponding storefront SKU/Pancake identities. Do not infer a mapping when this evidence is unavailable.

## Implemented authority boundaries

Browser occurrence endpoint: `POST /api/meta/events` accepts exactly one of `{eventId, path}` for PageView or `{receipt}` for a server-signed ViewContent/InitiateCheckout receipt. An extra `eventId` is rejected; receipt replay retains the signed event ID. The existing DB limiter enforces 60/minute per trusted-client hash before the 600/minute shared budget, so a denied client cannot exhaust that shared budget. UUIDv4, exact origin, content type, actual body-byte limit and a public path are validated. The server controls event names, price, items, quantity and value. There is no arbitrary `event_name`, `custom_data`, Purchase or AddToCart request interface.

A receipt contains a server occurrence UUID and rendered non-PII business facts, with a domain-separated HMAC and a 15-minute expiry. The existing server auth secret signs it; the secret and CAPI access token never cross the client boundary. Receipt construction alone causes no event: SSR/prefetch never sends CAPI. Only a browser effect signals the occurrence. Same-URL rerenders do not create another event. A cached Back revisit refreshes server facts and obtains a new receipt/ID before reporting the next occurrence. Pixel blocking does not suppress the independent first-party signal.

AddToCart uses the existing cart transaction's committed snapshot and `quantity - previousQuantity`. The public action returns only the non-PII Pixel parameters and event ID. CAPI is scheduled from the successful server mutation; the browser uses its returned ID. No network call to Meta sits inside a cart/order transaction.

Purchase stores attribution before the POS write so reconciliation needs no surviving browser request. The serialized event contains hashed identifiers and server-only attribution, but never the token. Readers for public success/tracking responses keep explicit allowlists; the browser purchase reader returns only total and content facts. `metaPurchaseSentAt` is set only after explicit API acceptance. Concurrent deliveries can occur but use the same frozen event identity/payload. This is not a distributed exactly-once guarantee. Validated acknowledgement clears `metaPurchaseContext` and strips `user_data`/`event_source_url` from the retained payload in the same write, keeping browser business facts. Seven-day expiry also redacts attribution, including unconfirmed/ambiguous submissions, in bounded maintenance from existing PageView/manual retry paths. Maintenance requires those paths to run; no worker/cron is introduced.

All CAPI URLs use the configured storefront origin and public path without queries. `_fbp`/`_fbc` cookies pass through unchanged after format checks, including current optional appendices. A missing `_fbc` can be derived only from a real `fbclid` on a same-origin browser referrer; organic traffic gets no fabricated click ID. IP comes only from the explicitly trusted proxy header.

- **Required:** account/Pixel/token/domain and live Meta acceptance/dedup remain unverified. No real account or production secret was available. Catalog mapping is a conditional checkpoint for a future catalog integration, not a prerequisite for website Pixel/CAPI tracking.

- **Required code findings:** none after the independent review of the follow-up fixes. Initial head `f93b32f6` passed all Linux GitHub checks; the follow-up head has its own new checks after push. This PR must remain unmerged per the owner instruction.
- **Consider:** non-Purchase delivery is bounded best effort, without a durable queue. A closed tab, blocked first-party signal or process termination can still lose an event. Purchase preserves replayable facts, but its outage replay is manual; there is no new worker/cron deployment in this scope.
- **Consider:** receipts expire after 15 minutes. A very old prefetched/restored page can show a Pixel event whose CAPI receipt is expired. Browser/delivery replay and cross-device Purchase visits beyond Meta's dedup window also need account-level review; localStorage is only a per-browser guard.
- **Consider:** endpoint signatures and shared limits bound anonymous signals; they do not prove a human browser. Confirm edge controls before scaling traffic. Bounded attribution maintenance runs on traffic/manual retry, so an idle deployment needs the existing retry command to perform expiry cleanup.

## Operation and manual verification

The app still uses a build-time `NEXT_PUBLIC_FACEBOOK_PIXEL_ID` tied to its CSP and a server-only runtime `FACEBOOK_CAPI_ACCESS_TOKEN`. `FACEBOOK_GRAPH_API_VERSION` defaults to v26.0. `FACEBOOK_CAPI_TEST_EVENT_CODE` is staging/Test Events only. Keep the real token out of shell output, client configuration, dataLayer and logging.

After an outage, `pnpm meta:purchase:retry` scans at most 20 confirmed, unacknowledged recent purchases. Standalone Node must receive the exact deployed `LA_BUILD_FACEBOOK_PIXEL_ID` explicitly: it does not guess from a runtime public Pixel variable. It retains stored conversion time/payload and records acknowledgement only on validated acceptance. The seven-day replay bound is a conservative local expiry policy; confirm the current account/API time-window restrictions before historical recovery. A failed scan can be rerun; no tracking operation changes an order's commerce state.

Before any later activation/deployment, manually verify:

1. Exact Pixel/dataset ID, token permission/scope and server runtime configuration; deployed CSP and source origin agree with the build.
2. Meta Test Events receives all five events. Browser/server names and IDs match; one deduplicated conversion results; Purchase uses publicCode and the earlier conversion time after reconciliation. Check acceptance warnings, Diagnostics and Event Match Quality, not just HTTP success.
3. A normal purchase, ambiguous POS write followed by reconciliation, transient delivery failure/replay, positive cart-page/drawer delta, decrease/no-op, ad-blocked Pixel, organic entry and actual ad-click entry.
4. `_fbp`/`_fbc` and trusted IP are observed on real requests; no invented fbc for organic traffic. Check that browser event parameters, network responses and dataLayer contain no CAPI token or customer identifiers. Review account automatic matching/event rules separately.
5. Catalog checkpoint: read actual `id`/`retailer_id` samples and distinguish product/variant mappings before any content ID semantics change. Verify eventual content matches, including product slug renames.
6. Actual domain verification/ownership, the selected conversion/domain configuration and allowed traffic/edge controls. This audit makes no change to those settings.

## Decisions

| ID | Topic | Decision |
|---|---|---|
| D-01 (R-01) | Stack pairing | Two campaigns stack only when **both** allow combining with each other (type-level and/or campaign-ID level, checked in both directions). Priority must be unique among campaigns acting on the same unit price. Campaigns without stack configuration keep today's behaviour (legacy overlap resolves to base price). Contradictory configuration at runtime fails closed with a warning; never random. |
| D-02 (R-02) | Legacy `FIXED_PRICE` in a stack | Acts as a **price ceiling**: `next = min(current, configuredFixedPriceVnd)`. Standalone semantics (final per-unit price) and historical data are unchanged. |
| D-03 (R-03) | Duplicate gift identity | When `allowDuplicateGifts = false`, at most one unit **per `ProductMirror`** within a campaign, regardless of variant. |
| D-04 (R-04) | Gift fulfilment | Only variants that can be delivered **READY** with proven capacity. No PREORDER/OVERSELL for free gifts. Composite gifts are allowed only when every component can be checked and reserved; until GQ17 delivers that, composite variants are excluded from gift allowlists. |
| D-05 (R-05) | FROM_REACHED_THRESHOLD | `N0 = min(minQuantity)` of the campaign. The discount value comes from the **highest reached tier**; it is applied to `Q − N0 + 1` units when `Q >= N0`, else 0. Discount values must be non-decreasing with the tier threshold. EX-19 holds (Q=3 → 100.000đ, Q=4 → 225.000đ). |
| D-06 | VND rounding | **Half-up with `BigInt` on each unit's price**, then group units into lines. Never round a line total and never average. `100.001 × 90% = 90.001`; `5 × 90% = 5` per unit, so 3 units = 15đ. |
| D-07 (R-07) | Category parent/child | Use the existing `category-taxonomy.ts` resolver (`categoryListingKeys`) and website-owned `ProductCategoryMembership`; promotions invent no hierarchy of their own. |
| D-08 | Pancake gift representation | See below. |
| D-09 | Persistence isolation (GQ03) | Gift and quantity-tier campaigns live in **their own tables and enums** (`GiftQuantityCampaign`, `GiftQuantityTarget`, `GiftQuantityFrozenProduct`, `QuantityTier`, `GiftOption`, `GiftQuantityStackPeer`), not as new `PromotionCampaignKind` values. Reason: legacy readers (candidate lookup, flash-sale/sale listings, Merchant, runtime health, order audit) select `PromotionCampaign` rows and would otherwise have to be audited and kept from pricing a row whose `discountType` is meaningless for the new rules; separate tables make that impossible by construction and leave legacy data, enums and constraints untouched. Lifecycle fields keep the same meaning and the same derived status; the lifecycle service shares the global `PromotionPricingRevision` lock and revision. Gate: `LA_GIFT_QUANTITY_PROMOTIONS_ENABLED`, exact `"true"`, independent of `LA_PROMOTION_ACTIVATION_ENABLED`. |
| D-10 | Stacking consent (GQ07) | The stacking engine is pure (`gift-quantity-stack.ts`). A **tier** campaign lists the peers it accepts (`GiftQuantityStackPeer`: legacy kind or campaign id, or `*`). A **legacy** campaign has no stacking fields and the legacy table is not changed; its consent will be a row in a separate additive table written by the GQ09a admin write contract. No consent row = not stackable = legacy behaviour exactly as today. When a tier and a legacy campaign share a unit and consent is missing or one-way, the **tier steps aside** and legacy keeps its price (a running Flash Sale never loses its discount because someone created a tier campaign); two new campaigns that cannot stack, or that tie on priority, **both** step aside. Conflicts are decided per campaign pair on the cart, never at random, and reported as `STACK_NOT_PERMITTED` / `STACK_PRIORITY_CONFLICT`. |
| D-11 | Order-value ladder (owner request 15/10/2026) | A QUANTITY_TIER campaign gains `tierBasis` (`QUANTITY`, or `ORDER_SUBTOTAL`; NULL reads as QUANTITY so every existing row and writer keeps its meaning). An `ORDER_SUBTOTAL` ladder is "from X ₫ of paid goods take Y % / Z ₫ off the order": thresholds are VND in the same `QuantityTier.minQuantity` column (INTEGER, <= 2.000.000.000), the highest reached rung wins (D-05), values never decrease with the threshold. It reuses the tier lifecycle, stacking, quote proof and order snapshot unchanged: its steps are `QUANTITY_TIER` steps, so no proof format, snapshot enum or POS projection changes. |
| D-12 | Order-value ladder: what is measured and where it runs | The threshold is the paid goods value **after every other discount** (legacy sale, quantity ladders), before shipping, gifts excluded (they are 0 ₫). The ladder therefore **always runs last** in the chain, whatever its priority, and its scope is the whole basket (`GLOBAL_ALL_PAID_LINES`, enforced by a database CHECK both ways: an `ORDER_SUBTOTAL` tier is global, a QUANTITY tier is not). Stacking uses the D-01/D-10 consent rules unchanged (a running Flash Sale never loses its discount). A ladder still under its first rung takes no part in conflict detection (as an idle quantity tier), and the cart only advertises "spend X more" for a ladder that, forced on, the engine would not set aside. |
| D-13 | Order-value ladder: units and money | `PERCENTAGE` is applied per unit, half-up with `BigInt` (D-06). `FIXED_AMOUNT_TOTAL_VND` is a **total off the order** (never valid on a QUANTITY ladder, and the value must be below the threshold that earns it). The POS only takes line prices, so the total `D` is split over units in proportion to price: each unit takes `floor(D*p/S)` and the `R < units` VND still owed go one apiece to the units with the largest fractional share (ties: dearer unit, variation id, line key; never input order), so the discounts add up to exactly `D` and units of one line differ by at most 1 VND (a line splits into at most two segments). As everywhere (FR-07) a unit that would fall under 1 ₫ drops the **whole** ladder (`TIER_PRICE_INVALID`), nothing is clamped. A basis cannot change once a campaign is Scheduled (copy to a new Draft), like a gift trigger. |

## D-08 — Pancake gift projection (owner request)

For accounting convenience the owner wants gift units sent to Pancake with **a price of 1.000đ per unit** (`GIFT_VENDOR_UNIT_PRICE_VND = 1000`, a single named constant owned by the adapter), with the same amount **deducted from the paid goods**, so the Pancake order total equals the website total exactly.

The website remains the authority. The change is confined to the *outbound vendor projection*:

1. **Website quote, proof and order snapshot are unchanged.** Gift lines stay `role = GIFT`, `unitPriceVnd = 0`; paid lines keep their exact segment prices. The buyer sees 0đ for gifts, the quote proof signs 0đ, analytics/Meta Purchase use the website snapshot (gifts contribute 0 revenue), shipping uses paid-only quantity and subtotal. The buyer never sees the 1.000đ.
2. **Projection (pure function, GQ20).** Input: the signed paid/gift lines. `G` = total gift units; `D = G × GIFT_VENDOR_UNIT_PRICE_VND` is the amount to deduct. Output lines for Pancake:
   - gift lines: `variation`, `quantity`, `unitPriceVnd = 1000` (grouped per variation);
   - paid lines: the same segments, except that a total of `D` đ is removed from paid *units*: iterate paid units ordered by unit price descending, then `lineId` ascending, then unit index; from each take `min(remaining, unitPrice − 1)` đ. The affected unit becomes its own line (quantity 1, reduced unit price); identical `(variation, price)` units are re-grouped.
   - The sum of projected lines **must equal** the sum of website paid lines. If `remaining > 0` after all units (the paid units cannot absorb `D` while each keeps a price ≥ 1đ) the projection is infeasible → fail closed (`VENDOR_PROJECTION_INFEASIBLE`), no POS call, buyer is re-quoted/blocked.
3. **Audit.** The projection that was sent (lines + hash) is stored with the order snapshot so reconciliation compares Pancake read-back against **the projection**, and compares order totals against the website total. Website lines are never rewritten to match the vendor shape.
4. **Idempotency/determinism.** The projection is a pure function of the signed lines; retries produce the identical payload.
5. **Consequence for the POS gate.** Case (a) “gift at 0đ” is no longer needed for the flow (a 1.000đ line is an ordinary positive custom price, the case P10 proved). The projection *does* always produce lines with the same `pancakeVariationId` and different unit prices when a gift/paid unit pair share a variant or when a deduction splits a paid segment, so cases (b) PAID+GIFT same variation and (c) PAID+PAID same variation different prices remain required at **API level**. The owner's screenshot shows the Pancake UI accepts several lines of one SKU with different prices (including 0đ and 7đ); that is UI evidence, not API evidence.

## Pancake gate (R-06) status

- No live Pancake call was made or authorised in this task. GQ01 delivers a probe script and runbook only; running it needs independent operator approval at execution time.
- Until API evidence for (b) and (c) exists, the gift and `FROM_REACHED_THRESHOLD` paths stay behind the default-OFF gate and no task may be reported as "live-verified". `ALL_ELIGIBLE_UNITS` tiers without gifts emit one line per variation/price and do not depend on (b)/(c).

## Consequences

- GQ01 probe cases become: (b′) PAID(P−1.000đ) + GIFT@1.000đ same variation; (c) PAID + PAID same variation / different price (EX-17, 290.003đ); (a) 0đ remains an optional informational case.
- GQ15 snapshot stores the vendor projection (lines + hash). GQ20 implements and unit-tests the projection with mocks. GQ21 reconciles read-back against the projection.
- Spec examples EX-13/EX-17/EX-18 gain a vendor-projection expectation; website-side expectations are unchanged.
- The 1.000đ amount is a constant in one place; changing it later is a code change plus ADR amendment, never a per-campaign setting.
- No change to legacy `FIXED_PRICE` data, catalog prices in Pancake, or historical orders.
